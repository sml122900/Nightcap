## React Native 제스처 엔진을 프로토타입 스펙 그대로 이식

**Problem**: 웹 프로토타입(vanilla JS/CSS)에 이미 검증된 스와이프 물리 값(임계값, 회전 계수, 스프링 커브)이 있었고, 이를 React Native(Reanimated + Gesture Handler)로 옮기면서 "손맛"을 그대로 재현해야 했다. 이후 제스처 체계 자체가 3방향(keep/drop/five)에서 4방향(보류/이전/삭제/별점모드)으로 전면 개편되는 요구사항 변경도 있었다.

**Action**: 프로토타입의 임계값·수식(upness/downness 분리, 프리필 공식)을 상수 파일로 격리해 코드와 스펙 문서(PROJECT.md)가 항상 대조 가능하게 만들었다. 드래그 중인 카드와 퇴장 애니메이션을 별도 컴포넌트로 분리해 연속 스와이프 시 다음 카드가 즉시 승격되도록 설계. 별점 모드는 도킹 애니메이션 + 0.5단위 별바 드래그를 Reanimated worklet과 `measure()`로 구현.

**Result**: 3방향→4방향 전면 개편을 기존 아키텍처(상수 격리, 퇴장 컴포넌트 분리)를 재사용하며 물리 엔진 파일은 건드리지 않고 이전/재작성 범위를 최소화. 타입체크·expo-doctor 통과, 실기기에서 크래시 없이 동작 확인.

## SQLite 기반 영속화 + 소프트 삭제 휴지통 설계

**Problem**: 메모리 배열 목데이터만 쓰던 앱에 처음으로 실제 데이터 영속성이 필요했고, "삭제"가 단순 배열 제거가 아니라 7일 유예 휴지통 + 세션 종료 시 사진첩 일괄 삭제 + 강제종료 후에도 삭제 큐가 유실되지 않아야 하는 복합 요구사항이었다.

**Action**: 버저닝된 마이그레이션 시스템(PRAGMA user_version)과 소프트 삭제(deleted_at) 컬럼으로 스키마를 설계. 사진첩 일괄 삭제 함수를 "이번 세션의 drop만"으로 좁히지 않고 "아직 asset이 남아있는 모든 drop 행"을 대상으로 일반화해, 세션 종료 트리거와 강제종료 복구 트리거가 같은 함수 하나를 공유하도록 만들었다.

**Result**: 별도의 "재시도 큐" 테이블이나 상태 플래그 없이, 쿼리 조건 하나로 정상 종료와 강제종료 복구를 모두 처리하는 단순한 설계로 귀결. 구현 전 계획을 서브에이전트로 교차검증해 스키마 필드 누락(kind/channel 컬럼)과 잠재적 자기모순(휴지통 쿼리가 목데이터에서 영구히 비는 문제)을 코드 작성 전에 발견해 재작업 없이 반영.

## 최신 SDK 문서 확인으로 런타임 폐기 API 사전 회피

**Problem**: 자주 바뀌는 Expo SDK에서 흔한 예제 코드(`deleteAssetsAsync`, `FileSystem.deleteAsync`)를 그대로 썼다면, 컴파일은 통과하지만 실기기에서 크래시가 나는 상황이었다(SDK57에서 구 API가 런타임 예외로 하드 폐기됨).

**Action**: 코드 작성 전 설치된 패키지의 실제 타입 선언(.d.ts)과 공식 버전별 문서를 직접 확인해, 클래스 기반 신규 API(`MediaLibrary.Asset.delete`, `new File(uri).delete()`)로 처음부터 정확하게 구현.

**Result**: 런타임에야 발견됐을 크래시를 구현 단계에서 회피, 추가 디버깅 사이클 없이 한 번에 정상 동작.

## 실제 스크린샷 스캔 파이프라인을 첫 렌더 차단 없이 통합

**Problem**: MediaLibrary 스캔·파일 복사·DRM 판별을 포함한 캡처 파이프라인은 느릴 수 있는 I/O 작업이 여러 단계 얽혀 있는데, 이를 앱 시작 초기화(`SQLiteProvider.onInit`)에 그대로 넣으면 스캔이 끝날 때까지 첫 화면 자체가 뜨지 않는 문제가 생긴다. 게다가 스캔 도중 사용자가 스와이프 중이거나 별점 모드를 쓰고 있으면, 새로 스캔된 카드가 그 상태를 깨뜨리지 않고 끼어들어야 했다.

**Action**: 스캔을 `initDb` 체인에서 제외하고 화면 마운트 이후 비동기로 실행하도록 분리했다. 스캔 결과는 기존 스택을 통째로 교체하지 않고, 진행 중인 카드/카운터를 건드리지 않는 append-only 병합으로 큐 꼬리에만 추가했다. 드래그·별점 모드 진행 여부를 ref로 추적해, 진행 중이면 병합을 대기열에 넣어뒀다가 제스처가 끝나는 순간 flush하도록 만들었다.

**Result**: 스캔이 아무리 오래 걸려도 앱 첫 화면 로딩 속도에 영향이 없고, 사용자가 스와이프 도중 새 스크린샷이 몰래 끼어들어 카드가 밀리거나 진행률이 튀는 일이 없어졌다. 실패 허용 설계(watermark를 실패 지점 이전으로 유지)까지 더해 강제종료·부분권한 상황에서도 재시도가 자동으로 되도록 구성.

**관련 커밋/PR**:

## AGP 버전 조건부 dead code로 인한 서드파티 라이브러리 빌드 실패를 config plugin으로 영속 수정

**Problem**: DRM 판별용으로 추가한 `react-native-image-colors`가 최신 Android Gradle Plugin(8+) 환경에서 자체 Kotlin/Java JVM 타깃 설정 코드가 조건부로 무시되면서 릴리즈 빌드 자체가 실패했다. `expo prebuild`가 네이티브 프로젝트를 매번 통째로 재생성하는 구조라, 생성된 파일을 직접 고쳐도 다음 빌드에서 사라지는 제약도 있었다.

**Action**: 실패 원인을 라이브러리의 `build.gradle` 소스까지 직접 추적해 "AGP<8에서만 적용되는 죽은 코드"라는 걸 확인했고, 루트 빌드 스크립트에 모든 서브프로젝트의 JVM 타깃을 강제하는 보정 로직을 추가했다. 처음엔 `afterEvaluate`로 시도했다가 `--configure-on-demand` 하에서 "이미 평가된 프로젝트" 예외를 만나, 평가 시점에 의존하지 않는 `pluginManager.withPlugin`/`tasks.withType` 방식으로 재작성했다. 이 로직은 생성된 `android/build.gradle`에 직접 넣지 않고, `expo prebuild`가 재실행돼도 자동 재적용되는 로컬 config plugin으로 만들었다.

**Result**: 코드 한 줄 건드리지 않고 서드파티 의존성의 구조적 결함을 프로젝트 차원에서 흡수하는 재사용 가능한 픽스를 만들어, 향후 같은 유형의 라이브러리를 추가해도 같은 실패가 재발하지 않도록 했다.

## 도그푸딩 피드백으로 코어 유입 경로를 전면 전환

**Problem**: 전 스크린샷을 무조건 자동으로 스택에 밀어넣는 최초 설계는, 실제로 며칠 써보니 업무 캡처·일회성 스크린샷까지 "정리해야 할 것"으로 쌓여 앱의 핵심 가치("도파민 루프의 출구")를 스스로 배반하는 문제를 낳았다. 게다가 유입 경로를 바꾸려면 "정리 모드가 유일한 기본 화면"이던 기존 네비게이션 구조 자체를 건드려야 했다.

**Action**: 유입 경로를 공유시트(의도적으로 보낸 것만) 주 경로 + 자동 스캔 옵션(기본 OFF)으로 재구성하고, 두 경로가 같은 스키마·같은 사본복사/DRM 판별 로직을 공유하도록 설계해 신규 로직을 최소화했다. 이 전환에 맞춰 "정리 모드가 유일한 화면"이던 구조에서 홈 화면을 분리해, 공유 수신 시엔 토스트만 띄우고 정리 모드로 끌고 가지 않도록 흐름을 재설계했다.

**Result**: 신규 설치 시 사진 권한 프롬프트가 아예 안 뜨는 온보딩 마찰 감소를 부수 효과로 얻었고, "낮의 캡처"와 "밤의 정리"라는 제품 정체성이 네비게이션 구조로 다시 명확해졌다. 두 유입 경로의 dedup(asset_id/content_hash)이 서로 간섭하지 않는 부분 유니크 인덱스 설계로, 기존 스캔 파이프라인 코드를 거의 재작성하지 않고 흡수했다.

**관련 커밋/PR**:

## "전부 로컬" 원칙과 기능 요구 사이의 트레이드오프를 좁은 예외로 설계

**Problem**: 공유된 링크(유튜브 등)의 카드 제목이 URL 그대로 표시돼 "어떤 콘텐츠였는지" 알 수 없다는 피드백이 나왔는데, 근본 원인은 안드로이드 공유 인텐트 자체가 콘텐츠 제목을 실어 보내지 않는다는 OS 레벨 제약이었다. 유일한 해법은 외부 네트워크 호출인데, 프로젝트는 "서버·계정·API 호출 없음"을 원칙으로 못박아 둔 상태였다.

**Action**: 원칙을 무너뜨리지 않는 선을 먼저 정의했다 — 키/계정/자체 서버가 필요 없는 공개 엔드포인트(oEmbed, og 태그)만, 실패해도 기능에 지장 없는 그레이스풀 폴백을 전제로 허용. 이 결정을 코드보다 먼저 CLAUDE.md 원칙 문구와 결정 문서에 명문화한 뒤 구현에 들어갔다. 로그인 벽 때문에 이 방식이 거의 항상 막히는 인스타/X는 "WebView로 로그인 세션을 재사용하면 되지 않나"까지 검토했지만, 앱과 브라우저 세션이 애초에 분리돼 있어 재사용할 게 없다는 걸 근거로 기각하고 URL 패턴 기반 최소 폴백으로 대체했다.

**Result**: 원칙 문서에 예외의 범위와 이유가 남아 향후 "이것도 예외에 해당하나?" 판단 기준이 생겼고, 3초 타임아웃 + 실패 시 무조건 조용한 폴백 설계로 오프라인/네트워크 실패가 기능 자체를 깨뜨리지 않는다. 하지 않기로 한 것(WebView 스크래핑)의 이유까지 기록해, 나중에 "왜 이건 안 했지"를 다시 검토하는 시간 낭비를 막았다.

## 백그라운드 빌드 타임아웃과 실제 완료 여부를 기기 아티팩트로 교차검증

**Problem**: 릴리즈 빌드+설치를 백그라운드로 실행했는데 컴파일에만 9분 넘게 걸려 지정한 타임아웃 한도에 거의 닿았고, 프로세스가 앱 실행 확인 단계에서 결국 타임아웃으로 강제 종료됐다. "프로세스가 죽었다 = 빌드 실패"로 단정하면 이미 성공한 빌드·설치를 처음부터 다시 반복하는 시간 낭비가 생길 상황이었다.

**Action**: 로그에 남은 "BUILD SUCCESSFUL"/"Installing"/"Opening" 라인을 근거로 빌드·설치 자체는 이미 끝났다고 판단하고, 프로세스 생존 여부 대신 기기 쪽 아티팩트(APK 파일 타임스탬프, `adb shell dumpsys package`의 `lastUpdateTime`)로 실제 설치 여부를 재확인하려 시도했다. 그 과정에서 기기가 재승인 팝업 없이 조용히 `unauthorized`로 되돌아가고 이어 USB 연결 자체가 끊기는 것도 함께 확인해, 원인을 "빌드 실패"가 아니라 "연결 문제"로 좁혔다.

**Result**: 재빌드 없이도 빌드·설치 성공 여부를 CLI 종료 코드가 아닌 기기 상태로 판단하는 절차를 문서화(`docs/troubleshooting/release-build-launch-confirmation-cut-off.md`)해, 다음 세션에서 같은 상황을 만나도 곧장 재확인 스텝으로 넘어갈 수 있게 됐다.

## 첫 실행 온보딩 도입 — 미사용 함수 재사용 + 초기 라우팅 깜빡임 제거

**Problem**: 첫 실행 시 "왜"(정체성)와 "어떻게"(공유시트 사용법)를 전달할 온보딩이 없었다. 그런데 앱의 기본 화면 상태는 `useState`로 즉시 `'home'`을 그리는 구조라, "온보딩을 완료했는가"를 SQLite 비동기 조회로 판단하면서도 화면 깜빡임(홈이 잠깐 보였다가 온보딩으로 바뀌는 식) 없이 라우팅해야 했다. 추가로, 정식 미디어 권한 요청 함수(`requestMediaAccess`)가 이미 구현돼 있었지만 실제로는 한 번도 호출된 적이 없었다(기존 스캔 경로는 권한이 없으면 그냥 조용히 스킵) — 온보딩이 이 함수를 처음 실사용하는 지점이었다.

**Action**: `RootNavigator`의 화면 상태 초기값을 `null`로 바꿔, DB에서 완료 플래그를 읽어올 때까지는 빈 화면만 렌더하고 `'home'`/`'onboarding'` 어느 쪽으로도 확정하지 않는 방식으로 깜빡임을 없앴다. 완료 플래그는 새 테이블·마이그레이션 없이 기존 `meta` key/value 테이블에 동일한 upsert 패턴으로 얹었다. 온보딩 3번째 페이지의 자동 수집 토글을 켤 때만 기존에 미사용 상태였던 `requestMediaAccess()`를 호출하고, 허용/거부 결과를 따로 분기하지 않은 채 그대로 진행하도록 설계했다 — 거부해도 스캔 파이프라인이 이미 권한 없으면 조용히 no-op하는 기존 방어 로직을 그대로 신뢰한 것이다.

**Result**: 신규 코드 대부분이 기존 패턴(meta 테이블 upsert, 진행률 바 색상 언어, 헤더 레이아웃)의 재사용으로 끝나, 순수 신규 로직은 초기 라우팅 분기와 3장 UI뿐이었다. 권한 결과에 대한 에러 핸들링을 아예 만들지 않았는데도 "허용/거부 둘 다 크래시 없이 진행 가능"이라는 요구사항을, 새 코드가 아니라 기존 파이프라인의 방어적 설계로부터 그대로 보장받았다.

## 21개 파일 리페인트를 "로직 변경 0"으로 유지하면서 3-서페이스 테마 시스템 도입

**Problem**: 다크 전용으로 만들어진 앱에 라이트 모드를 넣어야 했는데, 화면마다 테마를 따르는 규칙이 달랐다. 스와이프 덱은 화면 대부분이 사용자 스크린샷이라 라이트 모드에서도 어두워야 하고, 공유 카드는 `captureRef`로 PNG를 뽑는 출력물이라 뷰어 테마와 무관하게 항상 같아야 하며, 보관함 상세는 한 화면 안에서 이미지 영역과 편집 영역의 규칙이 갈렸다. `resolved === 'dark' ? A : B` 단일 이분기로는 표현되지 않았다. 게다가 기존 스타일이 전부 모듈 레벨 `StyleSheet.create`라 테마를 볼 수 없었고, 인라인 객체로 전환하면 매 렌더 재생성 비용이 붙었다.

**Action**: 토큰 이름을 늘리는 대신(원 지시서는 `cinemaBg`/`cinemaText` 같은 별도 이름을 제안했다) **팔레트를 하나 더 만들었다** — `cinema`는 `dark`를 덮어쓴 완전한 색 객체로, 이름은 `bg`/`textPrimary` 그대로고 값만 다르다. 공용 컴포넌트가 자기 문맥을 몰라도 되게 하려는 선택이었다(별도 이름이었다면 4개 공용 컴포넌트 내부에 문맥 분기가 들어갔을 것이다). 스타일은 `makeStyles((t) => ...)` 팩토리로 선언하고 훅으로 해소하되 **팔레트별로 결과를 캐시**해, 팩토리가 앱 수명 동안 최대 3번만 실행되도록 했다 — 비용 프로파일을 기존 모듈 레벨 시트와 동일하게 유지한 것이다. 대신 "팩토리 안에서 `mode`로 분기 금지"라는 제약이 생겨 주석으로 명시했다. 작업 중 지시서 표에 없어 그릴 수 없는 자리 3종(오버레이용 반투명 스크림, 스샷 위에 얹히는 전 팔레트 공통 딤, 골드 위 잉크)을 발견해 근거와 함께 토큰을 추가하고 보고했다.

**Result**: 색상 리터럴이 단일 파일에 수렴해 구 토큰 파일은 소비자 0으로 삭제됐고, `bg`를 순수 검정으로 되돌릴지 같은 후속 논의가 토큰 한 줄 수정으로 끝나는 구조가 됐다. 지시서에 "2번 커밋 후 다크가 이전과 픽셀 동일한지 확인" 이라는 검증 조건이 있었으나 지시서가 함께 준 새 팔레트 값 자체가 기존과 달라 성립할 수 없음을 지적하고 어느 쪽이 정본인지 확인받은 뒤 진행했다. 접근성 항목(터치 타겟 44pt 하한, 폰트 스케일 상한 1.4)도 같은 패스에서 정리.

## 검증을 위한 앱 삭제가 수집 중이던 계측 데이터를 지우는 상황을 사전에 차단

**Problem**: 밀려 있던 실기기 검증 3덩어리를 리빌드 1회로 소화하는 계획에서, 첫 항목인 온보딩 검증은 "앱 완전 삭제 후 설치"가 전제였다(그래야 첫 실행 플래그가 비어 온보딩 경로를 탄다). 그런데 그 기기에는 도그푸딩 계측이 2주째 쌓고 있던 `triage_sessions` 데이터가 있었다 — 다음 마일스톤(플로팅 버블) 도입 여부를 감이 아니라 데이터로 정하려고 앞선 라운드에서 통째로 만든 계측의 산출물이고, 지우면 재수집에 다시 2주가 든다. 지시받은 절차를 그대로 실행하면 이 손실이 조용히 발생하는 상황이었다.

**Action**: 삭제를 실행하기 전에 기기 상태를 먼저 조회해 실제 데이터 존재를 확인하고(`run-as`로 앱 샌드박스 열람), SQLite 파일과 샌드박스 캡처 이미지를 로컬로 추출했다. **Result**: 지시받은 작업을 축소하거나 미루지 않으면서도 되돌릴 수 없는 데이터 손실을 막았다. 부수적으로, 프로젝트 문서가 두 군데서 가리키던 "PROJECT.md §7 체크리스트"가 실재하지 않는 참조였음을 발견해 실제 체크리스트 문서를 만들고 참조를 교정했으며, 검증 순서(온보딩이 실패하면 뒤 항목이 도달 불가라 무의미하다는 의존성)와 보류 중인 결정 2건을 함께 기록해 다음 세션이 이어받을 수 있게 했다.

## 앱의 코어 루프를 통째로 막던 권한 게이트를, 실기기 검증으로 발견하고 경계를 재정의

**Problem**: 유입 경로를 자동 스캔에서 공유시트로 전환한 뒤에도 "사진 권한이 없으면 할 일이 없다"는 옛 전제 위에 세워진 가드가 남아 있었다. 그 결과 공유시트로 담은 카드(사진 권한이 전혀 필요 없는 데이터)가 쌓여 있어도 정리 화면 진입 자체가 차단됐고, 더 나쁘게는 온보딩이 정확히 그 상태를 만들었다 — 자동수집 토글을 켜면 권한 결과와 무관하게 ON으로 저장했기 때문에, 권한 팝업에서 거부한 신규 사용자는 앱의 핵심 기능이 통째로 죽은 상태로 착지했다. 크래시도 에러도 없어 코드만 읽어서는 드러나지 않았고, 실제로 이 결함은 릴리즈 빌드를 기기에 올려 온보딩부터 순서대로 밟아보는 검증에서야 발견됐다.

**Action**: 원인을 "권한이 죽여야 하는 것은 스캔 경로 하나뿐인데 화면 전체에 걸려 있다"로 정리하고, 진입 조건을 "정리할 카드가 있는가"만 남겼다. 권한 판단의 소유자는 스캔 함수 한 곳으로 모아 호출부의 중복 검사를 걷어냈다(거부 시 스캔만 조용히 건너뛰고 나머지 흐름은 그대로 간다 — 사용자가 이미 내린 선택이라 경고를 띄우지 않는 쪽을 택했다). 이어서 저장값이 실제 권한을 따라가도록 요청/동기화 함수를 만들어 온보딩과 설정이 같은 함수를 쓰게 했고, 그 과정에서 **지시받지 않은 두 번째 결함**(설정 화면은 권한을 요청조차 하지 않고 값만 저장하고 있었다)을 발견해 함께 고쳤다. 동기화는 마운트뿐 아니라 포그라운드 복귀 시점에도 돌게 했다 — 사용자가 시스템 설정에서 권한을 회수하고 돌아오는 경로는 화면이 마운트된 채여서 마운트 훅만으로는 잡히지 않기 때문이다.

**Result**: 사진 권한을 거부한 사용자도 공유시트로 담고 정리하고 별점을 매기는 전 과정을 쓸 수 있게 됐고, "공유시트를 주 경로로 한다"는 앞선 설계 결정이 비로소 실제로 성립했다. 원래 결함 조건을 인위적으로 재현해(권한을 준 상태로 토글을 켜 저장값을 남긴 뒤 권한만 회수) 진입이 되는 것까지 확인했다. 부수적으로 "설정 화면이 거짓말하지 않는다"는 원칙이 생겨, 이후 Android 14+ 제한적 접근 처리의 판단 기준이 됐다.

**관련 커밋/PR**: `aad4a31`, `98d4a1c`

## 라이브러리 문서와 실제 동작이 어긋나는 지점을 네이티브 소스로 특정

**Problem**: 제한적 사진 접근(Android 14+ "선택된 사진만 허용") 상태를 넓히라고 안내하는 버튼이 아무 일도 하지 않았다. `MediaLibrary.presentPermissionsPicker()`를 호출하는데 화면이 전혀 뜨지 않았고, 크래시도 예외도 없었다. SDK 문서에는 "사용자가 원래 limited를 허용한 경우에만 모달이 뜨고 그 외에는 no-op"이라고만 적혀 있어, 이게 테스트 환경의 한계인지 실사용에서도 재현되는 구멍인지 문서만으로는 가릴 수 없었다.

**Action**: 추측을 멈추고 `node_modules` 안의 네이티브 구현을 직접 읽었다. Android 쪽 델리게이트가 `presentPermissionsPicker`를 그냥 `requestPermissions`로 위임하고 있었다 — 즉 이 API는 별도의 "사진 재선택" 모달이 아니라 권한 재요청일 뿐이고, 사용자가 한 번 선택을 내린 뒤에는 OS가 아무것도 띄우지 않으므로 **도움이 필요한 바로 그 상태에서 조용히 실패**하는 구조였다. 제시된 두 가지 수정안 중 "호출 후 일정 시간 뒤 상태를 재확인해 폴백" 방식을 버리고 시스템 설정으로 단일화하는 쪽을 골랐는데, 근거는 세 가지였다: 모달이 떴는지 판별할 신호가 없어 타이밍 추정에 기대야 하고, 오탐하면 이미 열린 화면 위에 설정이 겹쳐 뜨는 더 나쁜 실패가 되며, 네이티브 구현상 그 경로가 제공하는 고유 능력이 없어 잃는 것이 없다는 점이다.

**Result**: 버튼이 "가끔 아무 일도 안 하는" 상태에서 "항상 목적지가 있는" 상태가 됐고, 실기기에서 시스템 설정 진입 → 권한 확대 → 복귀 시 안내 소멸 → 새 스크린샷 재유입까지 이어지는 흐름을 확인했다. 소비자가 사라진 래퍼 함수는 삭제하되 자리에 이유를 주석으로 남겨, 다음에 같은 API를 다시 집어들지 않게 했다. 조사 단계에서 내가 보고했던 전제 하나("선택기를 취소하면 항상 제한적 접근이 부여된다")도 이 라운드에서 재현 조건을 좁혀 정정했다 — 깨끗한 권한 상태에서는 성립하지 않는 관찰이었다.
