# ← 보류(hold)를 "내일 이월"에서 "즉시 2.5점 커밋"으로 변경

## Problem

초기 설계(PROJECT.md §1/§6/§7)는 ← 스와이프를 "보류"로 정의해 오늘 판정을 미루고 `held_count`를 올려 다음 날 스택 맨 위에 재등장시키는 이월 메커니즘이었다. 실기기로 직접 정리 모드를 돌려보니(도그푸딩), 이월은 "오늘 판정을 끝낸다"는 코어 루프(§1의 "반드시 끝나는 피드")의 체감 속도를 오히려 늦췄다 — 판정 자체는 스택에서 카드를 치워주지만, 아무 평가도 남기지 않고 그냥 다음날로 떠넘기는 선택지가 있으면 오히려 "후딱후딱 넘어가는" 손맛과는 맞지 않았다.

## Action

- ← 스와이프(및 대응 a11y "보류" 버튼)는 제스처/버튼 이름과 노출 라벨("보류")은 그대로 두되, 커밋 시점에 `verdict='rate', stars=2.5`(별점 모드의 "평가 생략" 기본값과 동일)로 즉시 확정하도록 바꿨다. 별점 모드 진입 없이 한 번의 스와이프로 끝난다.
- "내일 이월" 개념 자체를 제거: `held_count` 증가 로직(`applyVerdict`/`undoVerdict`의 `'hold'` 분기), `getTodayStack`의 `held_count DESC` 정렬을 삭제. `held_count` 컬럼과 `verdict` CHECK의 `'hold'` 값은 스키마에는 남지만(컬럼 삭제는 별도 마이그레이션이 필요하고 지금 단계에서 이득 대비 비용이 안 맞음) 이제 어떤 코드도 쓰지 않는다.
- 커밋 대상 `Verdict` 타입(`'drop' | 'rate'`)과, 아직 커밋되지 않은 제스처/버튼 액션을 나타내는 별도 `GestureAction`(`'hold' | 'drop'`) 타입을 분리했다 — "왼쪽 스와이프"라는 제스처 이름과 "DB에 실제로 쓰이는 판정"이 이제 다른 개념이라서다. 마찬가지로 퇴장 애니메이션 방향(왼쪽으로 날아가기 vs 위로 날아가기)도 커밋된 verdict와 무관하게 결정돼야 해서 `ExitKind`(`'hold' | 'drop' | 'rate'`)로 분리했다.
- `TriageSession`/`DoneScreen`의 "보류 · 내일로 이월" 집계 행과 안내 문구를 제거 — 이제 보류로 인한 항목도 전부 `rated`(평가한 캡처)로 집계되므로 별도 행이 의미가 없다.

## Result

- 왼쪽 스와이프 한 번으로 카드가 완전히 끝남(별점 모드 모달을 열 필요 없음) — "후딱후딱 넘어가게" 요구를 그대로 반영.
- `Verdict`/`GestureAction`/`ExitKind` 세 타입으로 나눈 덕분에 "제스처 이름", "DB에 쓰이는 값", "퇴장 애니메이션"이 서로 독립적으로 바뀔 수 있음 — 예를 들어 나중에 라벨 문구만 바꾸고 싶으면 `GestureAction`/UI 카피만 건드리면 되고 DB 스키마엔 영향 없음.
- `held_count`/`verdict='hold'`는 스키마에 흔적으로 남지만 완전히 죽은 값이라, 나중에 실제 스키마를 손볼 일이 생기면(예: 캡처 파이프라인 붙이는 마이그레이션) 그때 같이 정리하면 된다.
