# "전부 로컬" 원칙에 공개 URL 메타데이터 fetch를 예외로 허용

## Problem

공유시트로 URL을 받으면(§3.2) 제목 후보가 없을 때 `title`이 그냥 URL 문자열 그대로 저장됐다. 도그푸딩 중 "유튜브 공유해도 링크만 띡 표시되니 어떤 영상이었는지 모른다"는 문제가 확인됨 — 안드로이드 공유 인텐트가 애초에 영상 제목을 실어보내지 않기 때문에(OS/발신 앱 레벨 제약), 클라이언트에서 받은 인텐트만으로는 절대 알아낼 수 없다.

기존 "전부 로컬: 서버·계정·API 호출 없음" 원칙을 문자 그대로 지키면 이 문제는 영영 해결 불가.

## Decision

**좁은 예외를 허용한다**: 유저가 공유한 공개 URL 자체의 메타데이터(제목/썸네일)를, 그 URL이 속한 플랫폼의 **공개 엔드포인트**(oEmbed, `<meta property="og:...">`)에서 읽어오는 것만 허용.

조건:
- 키/계정/자체 백엔드 불요 — 순수 공개 GET 요청
- 유저 계정 데이터·행동 로그를 어디에도 전송하지 않음(요청 자체가 "이 URL의 공개 메타데이터 주세요"일 뿐)
- 타임아웃 3초, 실패(오프라인 포함)해도 기능은 그대로 동작 — URL 그대로 표시되는 기존 동작으로 조용히 폴백. 에러 팝업 없음.
- 이 예외 밖의 모든 것(계정 연동, 서버 동기화, 유저 데이터 업로드)은 여전히 원칙대로 금지 — Supabase 동기화/공유 링크는 PROJECT.md §9 "제외" 목록의 v2 백로그로 유지.

## 함께 결정: 인스타그램/X는 WebView·로그인 스크래핑 안 함

인스타그램/X(트위터)는 로그인 벽 때문에 oEmbed/og 파싱이 대부분 실패한다. "그럼 WebView로 로그인 세션을 재사용해서 긁으면 되지 않나"를 검토했으나 기각:

- 앱의 WebView 세션과 유저의 실제 인스타/X 앱(또는 브라우저) 로그인 세션은 분리돼 있어, 재사용할 로그인 상태 자체가 없다 — 결국 유저에게 앱 안에서 다시 로그인시켜야 하는데 이건 실효성 대비 마찰이 너무 큼.
- 메타/X 이용약관상 비공식 스크래핑은 계정 정지 리스크가 있고, 그 리스크를 유저 계정에 지운다는 게 부적절.
- 유지보수 비용 — 페이지 구조 바뀔 때마다 깨짐.

대신 URL 패턴 파싱(호스트+경로만 보고 "릴스"/"게시물"/"X 게시물 · @handle" 같은 최소 유형 라벨)과 공유 인텐트의 `EXTRA_TEXT`(URL 외의 문구가 있으면 제목 후보)로 대체. 완벽하진 않지만 fetch가 막힌 상황에서의 최선의 로컬 정보만 쓴다는 원칙과 일치.

## Result

- `services/urlMetadata.ts`: 유튜브 oEmbed 우선 시도 → 실패 시 일반 oEmbed 디스커버리 → 실패 시 og 태그 파싱. 셋 다 실패하면 조용히 URL 그대로.
- 썸네일은 URL을 DB에 저장하지 않고 기존 샌드박스 사본 파이프라인(`copyToSandbox`)으로 다운로드해 `image_uri`에 저장 — 원본 삭제/링크 만료에도 카드가 살아남는다는 기존 원칙(PROJECT.md)과 일관.
- fetch는 수신 즉시가 아니라 카드 INSERT 이후 비동기로 실행 — 카드는 즉시 뜨고 제목/썸네일은 도착 시 갱신(정리 세션 흐름을 막지 않음).
- 제목 수동 편집을 `kind==='drm'` 한정에서 전체로 확장 — fetch가 실패한 카드의 최종 폴백.
