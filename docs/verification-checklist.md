# 실기기 수동 검증 체크리스트

> **2026-08-09 1차 실행 결과는 맨 아래 "실행 기록"에 있다.** ①과 ③은 전부 통과했고,
> ②의 공유시트/클립보드 항목은 사람이 직접 해야 해서 남아 있다. 발견된 결함 3건도 거기 적혀 있다.

빌드/설치는 자동으로 확인되지만 "기능이 실제로 동작하는가"는 눈으로 봐야 아는 항목들. 밀린 것들을
리빌드 1회로 한 번에 소화한다.

**순서를 지킬 것.** ①이 실패하면 ②③ 결과가 전부 무의미하다(온보딩을 못 지나면 그 뒤 화면에
도달하지 못한다).

## 빌드

```powershell
$env:TMP='C:\tmp_expo'; $env:TEMP='C:\tmp_expo'; $env:GRADLE_USER_HOME='C:\gradle_home'
```
(한글 사용자 경로 때문에 필수 — `docs/troubleshooting/non-ascii-user-path-breaks-prebuild-and-gradle.md`)

`expo prebuild` → `gradlew assembleRelease` → `adb install -r`. **`am start` 금지** — 실행은 손으로.

**릴리즈 빌드로 검증하는 이유**: debug APK는 JS 번들을 Metro에서 받아오므로 USB(또는 무선 ADB)가
붙어 있어야만 뜬다. ②의 공유시트 흐름은 다른 앱에서 공유해 앱이 콜드 스타트되는 시나리오라
케이블을 달고 하면 부자연스럽고, Metro에 못 닿는 순간 그냥 빨간 화면이 된다. 릴리즈는 번들이
APK에 박혀 있어 완전히 독립적이다. 릴리즈 서명은 `signingConfigs.debug`로 잡혀 있어(RN 템플릿
기본값, `android/app/build.gradle`) 별도 키스토어 설정이 필요 없다.

**릴리즈에서 달라지는 것**: `__DEV__`가 false라 설정 화면의 개발자 통계 섹션이 자동으로 안 뜬다.
→ **설정 화면 맨 아래 `nightcap 1.0.0` 라벨을 5번 탭**하면 열린다(도그푸딩을 릴리즈로 하려고
만든 게이트라 의도된 동작).

**릴리즈로 하면 안 되는 것**: `bg` 값 비교(아래 "보류 중인 결정")는 값 하나 바꿀 때마다 재빌드라
릴리즈에 안 맞는다. 무선 ADB(`adb tcpip 5555`) + dev client로 따로 볼 것.

**릴리즈에선 `run-as`가 막힌다**(`package not debuggable`). 즉 앱 샌드박스를 열어볼 수도, 아래
백업을 되돌릴 수도 없다 — 복원이 필요하면 debug 빌드를 먼저 다시 깔아야 한다. 릴리즈 설치 여부는
`adb shell dumpsys package com.anonymous.nightcap`의 `flags`에 `DEBUGGABLE`이 없는 것으로 확인된다.

## 보류 중인 결정

### `bg`: `#000000` vs `#0B0D12`

현재 코드는 `#0B0D12`(디자인 시스템 지시서 값). 순수 검정으로 되돌릴 근거가 더 세다는 판단이 나온 상태:

- OLED 배터리 — 밤에 오래 켜두는 앱이다
- 스크린샷 콘텐츠의 명암비 — 커버가 화면 대부분을 차지한다
- 층위 구분은 `surface`(#14171F)가 이미 하고 있어서 `bg`만 순수 검정으로 내려도 위계가 안 무너진다

반대급부는 순수 검정의 스크롤 잔상(OLED smearing). **실기기에서 두 값을 눈으로 비교해 결정한다.**
시네마 `bg`(#08090C)도 같이 판단할 것. 결정 전까지 코드는 건드리지 않는다.

### 추출색 클램프(`app/src/theme/colorClamp.ts`)의 소비자

만들어뒀지만 지금 아무도 안 쓴다. 원래 후보였던 **보관함 셀 틴트는 무의미하다** — 셀에 커버 이미지가
꽉 차서 틴트가 보이지 않는다.

쓸 자리는 **LibraryDetail 메타 영역 배경** 하나. 이미지 아래 영역이 커버 색을 옅게 받으면
시네마↔테마 경계가 훨씬 자연스러워진다(위 ③에서 미검증 리스크로 잡아둔 바로 그 경계).

테스트 있는 순수 함수라 유지 비용이 0이므로 코드는 남긴다. **경계를 눈으로 보고 어색하면 그때 붙인다.**

### 발견된 결함

**[높음] 자동수집 ON + 사진 권한 없음 → 정리 모드 전체가 막힌다**

`TriageScreen`이 자동수집이 켜져 있을 때만 권한을 조회하고(`:188-193`), 그 결과가 거부면 덱 대신
`MediaAccessDeniedScreen`을 렌더한다(`:329`). 그런데 공유시트로 담은 카드는 사진 권한이 전혀 필요
없다 — 그런 카드가 5장 있어도 정리를 시작할 수 없었다.

문제는 **온보딩이 정확히 이 상태를 만든다**는 것이다. `OnboardingScreen.handleAutoScanToggle`은
`requestMediaAccess()` 결과와 무관하게 토글을 ON으로 저장한다. "자동 수집 켜볼까?" → 권한 팝업에서
거부 → 앱의 코어 루프가 통째로 막힌다. 실제로 이 경로로 재현했고, 설정에서 토글을 끄면 즉시 정상화됐다.

W3-1(스캔이 유일한 유입 경로) 시절의 가드가 W3-2(공유시트 주 경로)로 바뀔 때 함께 수정되지 않은
것으로 보인다. 이번 디자인 시스템 작업과는 무관하다. **기능 변경이라 손대지 않고 보고만 한다.**

**[중] 헤더 고스트 버튼이 44dp에 못 미친다**

전 화면 헤더의 "닫기"/"설정"/"공유"가 24.4×19.8dp다. `hitSlop={8}`을 더해도 40×36dp로 여전히 미달.
이번 터치 타겟 정리에서 칩·복원·링크해제·a11y 버튼·테마 세그먼트만 손보고 헤더는 빠뜨렸다.

**[중] 공유 카드 그리드 셀이 스펙과 정반대 비율로 렌더된다**

`ShareCardScreen`의 `cell`은 `aspectRatio: 0.72`(세로가 긴 포스터형)인데, 실측하면 263×204px로
가로/세로 **1.29**다. 높이가 대략 `width × 0.78`로 잡혀 있어 지정한 비율이 먹지 않은 것처럼 보인다
(0.72가 먹었다면 높이는 약 379px여야 한다). 결과적으로 공유 카드가 의도한 "세로 포스터 격자"가
아니라 가로 썸네일 나열이 된다.

이번 작업 이전(W3-3)부터의 동작이고, 이번엔 `borderRadius`/`backgroundColor`/`padding`만 토큰으로
바꿨을 뿐 `width`·`aspectRatio`는 건드리지 않았다. 원인은 더 파봐야 한다.

## 실행 기록 — 2026-08-09 (2차): 결함 1 수정 검증

`aad4a31`(진입 게이트 제거) + `98d4a1c`(토글 동기화) 반영한 릴리즈 빌드. `pm clear`로 데이터를

| # | 항목 | 결과 |
|---|---|---|
| 1 | 권한 없음 + 공유시트 카드 5장 → 정리 모드 진입 | **성공** (이전 빌드는 권한 거부 화면) |
| 2 | 권한 없음으로 정리 완주 | 에러·토스트 없이 Done 도달 |
| 3 | 온보딩 토글 ON → 권한 거부 → 설정 토글 | 아래 주석 참고 |
| 4 | 권한 회수 후 앱 복귀 → 토글 | **OFF로 정정**(두 번 재현) |
| 5 | 권한 허용 상태 스캔 회귀 | 정상 — 새 스크린샷이 스택에 유입됨 |

1번은 "자동수집 ON + 권한 없음"이라는 원래 결함 조건을 인위적으로 재현해서 확인했다
(권한을 준 상태로 토글을 켜 `meta`에 `1`을 남긴 뒤 `pm revoke`. 설정 화면을 열면 동기화가
정정해버리므로 열지 않고 곧장 정리 모드로 들어갔다).

5번은 사용자 사진첩을 건드리지 않고 검증했다. `pm clear`로 워터마크가 지워진 상태라 첫 스캔은
"지금부터"만 기록하고 기존 사진을 담지 않는다(설계대로). 그 뒤 **앱 화면을 스크린샷으로 찍어**
그것이 다음 스캔에 잡히는지 확인했다 — 유입된 건 사용자 사진이 아니라 검증용으로 만든 이미지다.
확인 후 그 카드를 삭제 판정해 사진첩에서도 지웠다.

### 3번에 대한 주석 — Android 15에서는 "거부"를 UI로 만들 수 없었다

온보딩에서 토글을 켜자 클래식 권한 다이얼로그가 아니라 **사진 선택기**가 떴고, 아무것도 고르지
않고 취소했는데도 `READ_MEDIA_VISUAL_USER_SELECTED`가 부여됐다. 그 결과 `MediaLibrary`는
`granted=true`(`limited`)를 반환하고, 토글이 ON으로 남는 것이 **정직한 상태**가 된다
(앱은 실제로 제한적 접근 권한을 갖고 있다). 결함이 아니다.

`READ_MEDIA_IMAGES`만 조회하면 `granted=false`라 "거부"로 오독하기 쉽다. 진짜 거부 상태는
두 권한을 모두 `pm revoke`해야 만들어지고, 그 상태에서 4번이 통과했다 — 3번이 검증하려던
"토글이 실제 권한을 따라간다"는 성질은 4번으로 확인된 셈이다.
